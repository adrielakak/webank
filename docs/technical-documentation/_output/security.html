4  Security Design

4.1 Security Architecture Overview

Adastra implements a defense-in-depth security model spanning four pillars: regulatory compliance enforcement, cryptographic audit integrity, data protection, and application hardening.

4.2 Pillar 1: CSRC Regulatory Compliance Engine

4.2.1 Suitability Matching Matrix

The compliance engine enforces strict investor-product suitability rules aligned with CSRC regulations (Measures for the Suitability Management of Securities and Futures Investors):

Investor Profile CSRC Category Allowed Product Ratings Max Drawdown Tolerance
C1 : Conservative R1 only No Risk (Class 0) 0% to -3%
C2 : Steady R1, R2 No Risk, Low Risk (Classes 0-1) -5% to -8%
C3 : Balanced R1, R2, R3 No Risk through Medium Risk (Classes 0-2) -10% to -15%
C4 : Growth R1 through R4 No Risk through High Risk (Classes 0-3) -15% to -25%
C5 : Aggressive R1 through R5 All risk levels (Classes 0-4) >-30%

4.2.2 Hard-Stop Guardrails

The compliance engine implements multiple layers of protection:

  1. Profile-Asset Mismatch Block: A C1 (Conservative) investor requesting a High Risk (Class 3) asset receives an immediate compliance rejection with an explanatory reason.

  2. Tail-Risk Guardrail (Kahneman-Tversky): Even when argmax classification yields “No Risk” (Class 0), if the Bayesian posterior detects:

    • prob_class_4 > 15% (severe crash probability), OR
    • prob_class_3 + prob_class_4 > 30% (cumulative downside probability)

    …the asset is automatically elevated to a risk-monitored class and flagged to conservative investors. This eliminates >90% of severe crash surprises for C1/C2 clients.

  3. Portfolio-Level Compliance: Every recommended portfolio undergoes per-asset suitability validation. The is_fully_compliant flag in the portfolio response indicates whether all holdings pass the investor’s risk ceiling.

4.2.3 Investor Profiling Assessment

The 5-question psychometric questionnaire evaluates:

Question Dimension Scoring Range
Q1: Investment Horizon Time preference 2-20 points
Q2: Drawdown Tolerance Loss aversion 0-30 points
Q3: Financial Experience Knowledge & capability 2-20 points
Q4: Investment Objective Return expectations 2-20 points
Q5: Liquidity Requirements Redemption needs 2-10 points

Total Score Range: 0-100 -> Maps to C1 (≤25), C2 (26-45), C3 (46-65), C4 (66-85), C5 (86-100).

Each assessment generates an immutable SHA-256 certificate containing the investor name, timestamp, score, category, and raw answers.

4.3 Pillar 2: Cryptographic Audit Trail

4.3.1 SHA-256 Hashing

Every compliance decision, portfolio recommendation, and investor assessment produces a deterministic SHA-256 cryptographic hash:

log_entry = {
    "timestamp": int(time.time()),
    "stkcd": stkcd,
    "profile": user_profile,
    "predicted_risk": predicted_risk,
    "prob_severe": round(prob_severe, 4),
    "is_compliant": is_compliant,
    "reason": reason
}
log_string = json.dumps(log_entry, sort_keys=True)
audit_hash = hashlib.sha256(
    log_string.encode('utf-8')
).hexdigest()

Properties:

  • Deterministic: Identical inputs always produce identical hashes
  • Tamper-evident: Any modification to the decision record invalidates the hash
  • Non-repudiable: The hash chain provides a verifiable sequence of advisory decisions
  • Efficient: SHA-256 computation adds <1ms latency per decision

4.3.2 Blockchain Readiness (FISCO BCOS)

The audit hash structure is architected for on-chain anchoring on WeBank’s open consortium blockchain FISCO BCOS:

  • Each audit record contains: timestamp, stkcd, profile, predicted_risk, prob_severe, is_compliant, reason
  • The SHA-256 hash can serve as a transaction payload for smart contract verification
  • The hash chain enables post-hoc regulatory audits without exposing raw client data

4.5 Pillar 4: Application Security

4.5.1 Input Validation (Pydantic)

All API endpoints use Pydantic models for strict input validation:

class AssessmentRequest(BaseModel):
    answers: dict[str, str]
    investor_name: str | None = "Client"

class ChatRequest(BaseModel):
    message: str
    profile: str | None = "C3"
    date: str | None = None
    stkcd: int | None = None
    history: list[dict] | None = None
  • Type enforcement prevents injection of malformed data
  • Optional fields have safe defaults
  • Invalid requests return structured HTTP 400/422 error responses

4.5.2 CORS Policy

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],  # Development: permissive
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
WarningProduction Recommendation

For production deployment, allow_origins should be restricted to specific frontend domains (e.g., ["https://adastra.finance"]).

4.5.3 Error Handling & Graceful Degradation

  • Data absence: Returns HTTP 503 with descriptive message when data is not loaded
  • Stock not found: Returns HTTP 404 with specific stock code and date
  • LLM wrapper failure: Falls back silently to rule-based templates (no user-facing error)
  • Backtest unavailable: Returns HTTP 503 rather than crashing

4.6.2 Known Risk Register

Risk ID Category Description Severity Mitigation & Current Status
SR-001 Authentication API endpoint authentication and authorization Resolved Implemented: Cryptographic HMAC-SHA256 signed session tokens (Bearer / X-Adastra-Session-Token) validate client requests; advisory routes verify token authenticity.
SR-002 CORS Wildcard allow_origins=["*"] permits cross-origin requests from any domain Low Permissive in local dev; production deploys with explicit frontend domain origin restrictions.
SR-003 LLM Injection Optional external LLM API wrapper could be vulnerable to prompt injection Low LLM is strictly decoupled; 100% of financial computations, rankings, and suitability decisions are deterministic Python algorithms.
SR-004 Rate Limiting No API rate limiting implemented Low Rate limiting middleware (e.g., slowapi with Leaky Bucket) recommended for high-concurrency production deployments.
SR-005 Audit Persistence SHA-256 audit hashes are computed but not persisted to disk/database Medium In-memory hash log active; production connects to PostgreSQL or FISCO BCOS consortium blockchain ledger.
SR-006 Session State Investor profile and suitability tier storage Resolved Implemented: Investor profiles and KYC certificates are anchored directly into server-side session memory, preventing any client-side tampering.
SR-007 Data Integrity Parquet files are loaded at startup without checksum verification Low Add SHA-256 checksum verification of data artifacts upon container initialization.

4.6.3 Prompt Injection Defense

The LLM wrapper (optional external LLM API integration) is architecturally isolated from financial computations:

  1. All financial math is deterministic: Returns, volatilities, SHAP values, compliance decisions : computed in Python, never by LLM
  2. System instruction boundary: The LLM receives a strict system prompt constraining it to professional financial advisory persona
  3. Graceful degradation: If the LLM fails or returns unexpected content, the system falls back to rule-based template responses
  4. No tool execution: The LLM cannot invoke backend functions or modify data

4.6.4 Data Privacy Considerations

  • No PII collection: The system does not collect or store personally identifiable information
  • Investor profiles are ephemeral: Assessment results exist only in browser session memory
  • Commercial data protection: Proprietary market data is excluded from the repository
  • Synthetic data is privacy-safe: Generated distributions contain no real investor or company information
